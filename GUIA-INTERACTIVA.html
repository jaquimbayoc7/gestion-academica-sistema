Visión General del Sistema

El Sistema de Gestión Académica es una aplicación full-stack compuesta por 3 servicios independientes que se comunican entre sí. Cada servicio corre dentro de un contenedor Docker, lo que permite levantarlos con un solo comando.

¿Cómo se conectan?

El usuario abre el navegador en http://localhost:3000 (Frontend). Cuando hace clic en "Crear Estudiante", el frontend envía una petición HTTP POST al backend (http://localhost:3001/api/v1/estudiantes). El backend valida los datos, aplica reglas de negocio y usa Prisma para guardar en PostgreSQL. La respuesta vuelve al frontend que actualiza la tabla.

Docker — Orquestación de Servicios

Docker empaqueta cada parte del sistema (base de datos, backend, frontend) en contenedores aislados que se comunican entre sí. docker-compose.yml define los 3 servicios y con docker compose up se levantan todos.

¿Por qué healthcheck?

Sin el healthcheck, el backend podría arrancar antes de que PostgreSQL esté listo para recibir conexiones. Con condition: service_healthy, Docker espera a que pg_isready confirme que la BD está lista antes de iniciar NestJS.

Base de Datos — Prisma ORM + PostgreSQL

El archivo schema.prisma define TODA la estructura de la base de datos: entidades, campos, tipos y relaciones. Prisma genera automáticamente las migraciones SQL y un cliente TypeScript tipado.

Relaciones clave

  • AsignacionDocente es la tabla intermedia: vincula un Docente + una Asignatura + un Período. "El profesor X dicta Cálculo I en 2026-A".
  • Matrícula vincula un Estudiante con una AsignacionDocente. "Juan se inscribe en Cálculo I con el profesor X".
  • Calificación es 1:1 con Matrícula. Cada matrícula tiene máximo UNA calificación con 3 notas parciales.

¿Cómo se traduce schema.prisma a SQL?

schema.prisma
model Estudiante { id Int @id @default(autoincrement()) nombres String codigo String @unique programaId Int programa ProgramaAcademico @relation( fields: [programaId], references: [id]) @@map("estudiantes") }
SQL Generado (migración)
CREATE TABLE "estudiantes" ( "id" SERIAL PRIMARY KEY, "nombres" TEXT NOT NULL, "codigo" TEXT NOT NULL UNIQUE, "programaId" INTEGER NOT NULL, CONSTRAINT "fk_programa" FOREIGN KEY ("programaId") REFERENCES "programas_academicos"("id") );

Código Real de Cada Capa — Módulo de Estudiantes

¿Qué es un DTO?

Un Data Transfer Object define la forma exacta de los datos que el cliente debe enviar. Los decoradores de class-validator validan automáticamente cada campo. Si faltan datos o tienen formato incorrecto, NestJS retorna error 400 sin ejecutar ninguna lógica.

dto/create-estudiante.dto.ts import { IsString, IsEmail, IsInt, IsDateString } from 'class-validator'; export class CreateEstudianteDto { @IsString() // ← Debe ser un string nombres: string; @IsString() apellidos: string; @IsString() codigoEstudiantil: string; @IsString() documentoIdentidad: string; @IsEmail() // ← Debe tener formato email correoInstitucional: string; @IsDateString() // ← Debe ser fecha ISO "2000-05-15" fechaNacimiento: string; @IsInt() // ← Debe ser entero (FK al programa) programaAcademicoId: number; }
dto/update-estudiante.dto.ts // PartialType hace todos los campos OPCIONALES // PUT { "nombres": "Juan" } → Solo actualiza el nombre import { PartialType } from '@nestjs/mapped-types'; import { CreateEstudianteDto } from './create-estudiante.dto'; export class UpdateEstudianteDto extends PartialType(CreateEstudianteDto) {}

¿Qué hace el Controller?

El Controller solo maneja HTTP: recibe la petición, extrae los datos y delega al Service. No contiene lógica de negocio ni accede a la base de datos.

controller/estudiantes.controller.ts @Controller('estudiantes') // → /api/v1/estudiantes export class EstudiantesController { // NestJS inyecta el Service automáticamente (DI) constructor(private readonly estudiantesService: EstudiantesService) {} @Get() // GET /api/v1/estudiantes findAll() { return this.estudiantesService.findAll(); } @Get(':id') // GET /api/v1/estudiantes/1 findOne(@Param('id', ParseIntPipe) id: number) { return this.estudiantesService.findOne(id); } @Post() // POST /api/v1/estudiantes + body JSON create(@Body() dto: CreateEstudianteDto) { return this.estudiantesService.create(dto); } @Put(':id') // PUT /api/v1/estudiantes/1 + body JSON update(@Param('id', ParseIntPipe) id: number, @Body() dto: UpdateEstudianteDto) { return this.estudiantesService.update(id, dto); } @Delete(':id') // DELETE /api/v1/estudiantes/1 remove(@Param('id', ParseIntPipe) id: number) { return this.estudiantesService.remove(id); } }

¿Qué hace el Service?

El Service contiene la lógica de negocio: verifica existencia, maneja errores de duplicidad (Prisma P2002) y lanza excepciones HTTP legibles. No conoce HTTP ni Prisma directamente.

service/estudiantes.service.ts @Injectable() export class EstudiantesService { constructor(private readonly repo: EstudiantesRepository) {} findAll() { return this.repo.findAll(); } async findOne(id: number) { const estudiante = await this.repo.findOne(id); if (!estudiante) throw new NotFoundException(`Estudiante con ID ${id} no encontrado`); // ↑ NestJS convierte esto en HTTP 404 automáticamente return estudiante; } async create(dto: CreateEstudianteDto) { try { return await this.repo.create(dto); } catch (error) { if (error.code === 'P2002') // ← Error de Prisma: UNIQUE violation throw new ConflictException('Ya existe con ese código o correo'); // ↑ NestJS convierte esto en HTTP 409 throw error; } } async update(id, dto) { await this.findOne(id); // ← Verifica existencia (lanza 404 si no) // ... similar a create con try/catch P2002 } }

¿Qué hace el Repository?

El Repository ejecuta las consultas a PostgreSQL usando Prisma Client. Encapsula el acceso a datos para que el Service no conozca SQL ni Prisma. Si se cambiara de BD, solo se modificaría este archivo.

repository/estudiantes.repository.ts @Injectable() export class EstudiantesRepository { constructor(private readonly prisma: PrismaService) {} findAll() { return this.prisma.estudiante.findMany({ // include es como un LEFT JOIN → trae el programa asociado include: { programaAcademico: true }, orderBy: { id: 'asc' }, }); } findOne(id: number) { return this.prisma.estudiante.findUnique({ where: { id }, include: { programaAcademico: true }, }); } create(dto: CreateEstudianteDto) { return this.prisma.estudiante.create({ data: { ...dto, fechaNacimiento: new Date(dto.fechaNacimiento) }, include: { programaAcademico: true }, }); } remove(id: number) { return this.prisma.estudiante.delete({ where: { id } }); } }

¿Qué hace el Module?

El Module ensambla las 3 capas: registra el Controller, el Service y el Repository. NestJS usa esta información para crear el árbol de dependencias e inyectar automáticamente cada clase donde se necesite.

estudiantes.module.ts @Module({ controllers: [EstudiantesController], // ← Registra endpoints HTTP providers: [ EstudiantesService, // ← Lógica de negocio EstudiantesRepository, // ← Acceso a datos ], }) export class EstudiantesModule {}

Caso Especial: Cálculo de Nota Definitiva

Fórmula

notaDefinitiva = nota1 × 0.30 + nota2 × 0.30 + nota3 × 0.40
El cálculo se hace en el CalificacionesService (lógica de negocio), NO en el Controller ni en el Repository. Si alguna nota es null, la definitiva queda pendiente.

calificaciones.service.ts — calcularDefinitiva() private calcularDefinitiva(nota1?, nota2?, nota3?): number | undefined { if (nota1 != null && nota2 != null && nota3 != null) { return Math.round((nota1 * 0.3 + nota2 * 0.3 + nota3 * 0.4) * 100) / 100; } return undefined; // ← Se guarda como NULL en la BD } // Ejemplo: nota1=4.0, nota2=3.5, nota3=4.5 // definitiva = (4.0×0.30) + (3.5×0.30) + (4.5×0.40) // = 1.20 + 1.05 + 1.80 = 4.05

Frontend — Next.js + React + Tailwind

El frontend usa Next.js 15 con App Router. Cada módulo CRUD tiene su página, servicio e interfaz TypeScript. La comunicación con el backend se centraliza en lib/api.ts.

¿Cómo funciona una página CRUD?

Patrón Formulario Dual (Crear / Editar)

El mismo formulario se usa para crear y editar. La variable editingId determina el modo:

  • editingId === null → Modo crear (llama a service.create())
  • editingId === 5 → Modo editar (llama a service.update(5, data))

Glosario de Conceptos

Haz clic en cada concepto para expandir la explicación:

Inyección de Dependencias (DI)

En lugar de que una clase cree sus propias dependencias (new EstudiantesService()), NestJS las inyecta automáticamente en el constructor. Esto funciona gracias al decorador @Injectable() y al registro en providers del módulo.

// NestJS hace esto automáticamente: const prisma = new PrismaService(); const repo = new EstudiantesRepository(prisma); const service = new EstudiantesService(repo); const controller = new EstudiantesController(service);
ValidationPipe + class-validator

El ValidationPipe (configurado globalmente en main.ts) intercepta el body de cada petición y lo valida contra el DTO usando decoradores de class-validator. Si falla, retorna HTTP 400 sin ejecutar ninguna lógica.

  • whitelist: true → Elimina campos que no estén en el DTO
  • forbidNonWhitelisted: true → Error si envían campos extra
  • transform: true → Convierte "1" a 1
HttpExceptionFilter

Captura todas las excepciones HTTP y las formatea en un JSON uniforme. Sin este filtro, cada tipo de error tendría un formato diferente.

// Formato uniforme de error: { "statusCode": 404, "message": "Estudiante con ID 99 no encontrado", "error": "NotFoundException", "path": "/api/v1/estudiantes/99", "timestamp": "2026-04-12T10:30:00.000Z" }
ResponseInterceptor

Envuelve todas las respuestas exitosas en la estructura { statusCode, message, data }. El frontend siempre sabe que el dato real está en json.data.

'use client' en Next.js

Next.js renderiza componentes en el servidor por defecto. Cuando un componente necesita useState, useEffect o eventos del navegador (onClick), debe marcarse con 'use client' al inicio del archivo para indicar que se ejecuta en el navegador.

Route Group → (dashboard)

La carpeta (dashboard)/ usa paréntesis, lo que la convierte en un Route Group de Next.js. Esto agrupa páginas bajo un mismo layout (con Sidebar) sin añadir el segmento a la URL. La ruta real es /estudiantes, no /dashboard/estudiantes.

Prisma — include y @relation

@relation en el schema define las Foreign Keys. include: { programaAcademico: true } en el código equivale a un LEFT JOIN SQL, trayendo la entidad relacionada anidada en el resultado JSON.

// Prisma findMany con include: { id: 1, nombres: "Juan", programaAcademico: { id: 1, nombre: "Ing. Sistemas" } } // Equivale a SQL: SELECT e.*, p.* FROM estudiantes e LEFT JOIN programas_academicos p ON e.programaAcademicoId = p.id
CORS — Cross-Origin Resource Sharing

El frontend (puerto 3000) y el backend (puerto 3001) son orígenes diferentes. Sin CORS habilitado, el navegador bloquearía las peticiones. En main.ts, app.enableCors() autoriza al frontend a comunicarse con el backend.

Errores de Prisma — P2002 y P2003
  • P2002 → Violación de UNIQUE. Ejemplo: intentar crear dos estudiantes con el mismo codigoEstudiantil. El Service lo captura y lanza ConflictException (HTTP 409).
  • P2003 → Violación de FOREIGN KEY. Ejemplo: intentar eliminar un programa que tiene estudiantes asociados.
