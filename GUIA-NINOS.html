🤔 ¿Por qué están separados?

¡Muy buena pregunta! El frontend y el backend están separados como piezas de LEGO 🧱. Si algo falla en la cocina (backend), el restaurante (frontend) puede seguir abierto mostrando un mensaje de "estamos arreglando algo". Y si cambias la decoración del restaurante, la cocina no necesita cambiar nada.

💬 ¿Cómo hablan entre ellos?

El frontend y el backend hablan usando un idioma especial llamado HTTP. Son como cartas que se envían por internet. Cada carta tiene un tipo: ¿quiero algo? ¿mando algo nuevo? ¿cambio algo? ¿borro algo?

📦 ¿Cómo se ven los mensajes?

📤 El frontend ENVÍA (petición)

Cuando creas un estudiante, el frontend envía esta "carta" al backend:

// Destino de la carta POST http://localhost:3001/api/v1/estudiantes // El sobre (headers) Content-Type: application/json // El contenido (body) { "nombres": "Juan Carlos", "apellidos": "Pérez Gómez", "codigoEstudiantil": "EST-2026-001", "programaAcademicoId": 1 }
📥 El backend RESPONDE

El backend siempre responde con este formato especial (nuestro ResponseInterceptor):

// Código de éxito HTTP/1.1 201 Created // La respuesta envuelta { "statusCode": 201, "message": "Created", "data": { "id": 1, "nombres": "Juan Carlos", "apellidos": "Pérez Gómez" } }

🚀 El viaje de un mensaje

Cuando haces clic en "Guardar estudiante" en el navegador, el mensaje recorre 5 paradas antes de volver con la respuesta. ¡Haz clic en cada parada para ver qué pasa!

🌐 Parada 1: Tu navegador (Frontend)

Aquí empieza todo. Tú escribes el nombre del estudiante en el formulario y haces clic en "Guardar". React llama a la función handleSubmit(), que a su vez llama al estudiantesService.create(dto). El service llama a apiPost() que usa fetch() para enviar la petición HTTP al backend. ¡El formulario se bloquea y aparece un loading mientras espera!

🎒 Paso a paso: "Crear un estudiante"

1

Llenar el formulario (Frontend)

En la página /estudiantes el usuario escribe: nombre, apellidos, código, correo, programa. Cuando hace clic en "Guardar", React ejecuta la función handleSubmit().

setLoading(true) // 🔄 Mostrar spinner
2

Llamar al service (Frontend)

El componente llama a estudiantesService.create(formData). Este service llama a apiPost('/estudiantes', formData) que usa fetch().

const result = await estudiantesService.create(dto)
3

Llega al Controller (Backend)

NestJS recibe la petición POST. El ValidationPipe verifica el DTO. Si está OK, el controller llama a estudiantesService.create(dto).

@Post() create(@Body() dto: CreateEstudianteDto)
4

Lógica de negocio (Service)

El service verifica que no exista un estudiante con el mismo código. Si existe, lanza ConflictException (error 409). Si no, llama al repository.

if (error.code === 'P2002') throw new ConflictException(...)
5

Guardar en PostgreSQL (Repository)

El repository llama a Prisma: prisma.estudiante.create({ data: dto }). Prisma genera el SQL y ejecuta el INSERT en PostgreSQL. Devuelve el estudiante con su ID nuevo.

INSERT INTO "estudiantes" ("nombres", ...) VALUES (...) RETURNING *
6

La respuesta viaja de vuelta

Los datos suben por todas las capas. El ResponseInterceptor los envuelve en { statusCode, message, data }. El frontend recibe el JSON y actualiza la tabla con el nuevo estudiante. ¡Éxito! 🎉

setEstudiantes([...estudiantes, nuevoEstudiante])

💻 ¿Cómo se ve en el código real?

Ahora veamos cómo el frontend llama al backend en el código real. ¡No te asustes! Lo explicamos parte por parte. 🧩

🌐 El mensajero central

lib/api.ts es el mensajero que todos los services del frontend usan. Tiene 4 funciones: apiGet, apiPost, apiPut, apiDelete. Cada función usa fetch() de JavaScript para enviar mensajes HTTP al backend. La variable NEXT_PUBLIC_API_URL guarda la dirección del backend (http://localhost:3001).

frontend/src/lib/api.ts // La dirección del backend (cocina) const BASE_URL = process.env.NEXT_PUBLIC_API_URL; // = "http://localhost:3001" // 📥 PEDIR datos → GET export async function apiGet<T>(path: string): Promise<T> { const res = await fetch(`${BASE_URL}/api/v1${path}`); // La respuesta viene con { statusCode, message, data } const json = await res.json(); return json.data; // ← Solo nos importa el data } // 📤 ENVIAR datos nuevos → POST export async function apiPost<T>(path: string, body: unknown): Promise<T> { const res = await fetch(`${BASE_URL}/api/v1${path}`, { method: 'POST', headers: { 'Content-Type': 'application/json' }, body: JSON.stringify(body), // Convierte objeto → texto JSON }); const json = await res.json(); return json.data; } // ✏️ ACTUALIZAR → PUT | 🗑️ BORRAR → DELETE // (misma lógica, diferente method)

¿Por qué json.data?

Nuestro backend siempre responde en este formato gracias al ResponseInterceptor:

{ statusCode: 200, message: "OK", data: [aquí van los datos reales] }

Entonces json.data saca solo la parte interesante. ¡Como abrir un regalo y quedarte con el juguete, no con la caja!

🔗 El traductor del frontend

Cada módulo tiene su archivo en services/. El service del frontend es el intermediario entre la página y el cliente HTTP. Agrupa todas las llamadas de un módulo en un solo lugar. Si mañana cambia la URL del backend, solo cambias este archivo.

frontend/src/services/estudiantes.service.ts import { apiGet, apiPost, apiPut, apiDelete } from '../lib/api'; import { Estudiante } from '../interfaces/estudiante.interface'; export const estudiantesService = { // Trae TODOS los estudiantes findAll: () => apiGet<Estudiante[]>('/estudiantes'), // → GET http://localhost:3001/api/v1/estudiantes // Trae UN estudiante por ID findOne: (id: number) => apiGet<Estudiante>(`/estudiantes/${id}`), // CREA un estudiante nuevo create: (dto: Partial<Estudiante>) => apiPost<Estudiante>('/estudiantes', dto), // ACTUALIZA un estudiante update: (id: number, dto: Partial<Estudiante>) => apiPut<Estudiante>(`/estudiantes/${id}`, dto), // ELIMINA un estudiante remove: (id: number) => apiDelete(`/estudiantes/${id}`), // Historial académico (HU-14) historial: (id: number) => apiGet<any>(`/estudiantes/${id}/historial`), };

📄 La página React

Cada página es un componente React con 'use client'. Usa useState para guardar datos en memoria y useEffect para cargar datos cuando la página abre. Todo lo que ve el usuario está aquí.

frontend/src/app/(dashboard)/estudiantes/page.tsx (simplificado) 'use client'; // ← "Esto corre en el navegador" import { useState, useEffect } from 'react'; import { estudiantesService } from '@/services/estudiantes.service'; export default function EstudiantesPage() { // 📦 Caja donde guardamos la lista const [estudiantes, setEstudiantes] = useState([]); // ⏳ ¿Estamos cargando? const [loading, setLoading] = useState(false); // ❌ ¿Hubo un error? const [error, setError] = useState(null); // 🚪 Al abrir la página → cargar estudiantes useEffect(() => { load(); }, []); async function load() { setLoading(true); try { const data = await estudiantesService.findAll(); setEstudiantes(data); // ← Actualiza la pantalla } catch { setError('Error al cargar'); } finally { setLoading(false); } } // 💾 Al guardar el formulario async function handleSubmit(formData) { await estudiantesService.create(formData); load(); // ← Recarga la lista } return ( <div> {loading && <p>⏳ Cargando...</p>} {error && <p>❌ {error}</p>} {/* tabla con estudiantes */} </div> ); }

🎣 Los «anzuelos» de React

En React, los Hooks son funciones especiales que le dan «superpoderes» a los componentes. Los dos más importantes para manejar peticiones HTTP son useState (memoria) y useEffect (efectos secundarios). Sin ellos, la pantalla no se actualizaría cuando llegan los datos del backend.

📦 useState — Las cajas de memoria

Imagínalo así:

useState es como tener cajitas en tu cuarto. Cada cajita guarda algo: ¿estoy cargando?, ¿tengo datos?, ¿hubo un error?. Cuando cambias algo dentro de la cajita, React redibuja la pantalla automáticamente. ¡Como magia! 🪄

useState — cómo funciona // 📦 Sintaxis: const [valor, setValor] = useState(valorInicial) // Cajita 1: la lista de estudiantes (empieza vacía) const [estudiantes, setEstudiantes] = useState<Estudiante[]>([]); // ↑ leer valor ↑ cambiar valor ↑ valor inicial // Cajita 2: ¿estamos esperando respuesta del backend? const [loading, setLoading] = useState(false); // → true mientras el fetch() está volando // → false cuando llega la respuesta // Cajita 3: mensaje de error (null = sin error) const [error, setError] = useState<string | null>(null); // Cajita 4: mostrar/ocultar el formulario const [showForm, setShowForm] = useState(false); // Cajita 5: el estudiante que estamos editando const [editing, setEditing] = useState<Estudiante | null>(null); // ────────────────────────────────────── // ⚠️ REGLA DE ORO: Nunca modifiques el valor directamente // ❌ MAL: estudiantes.push(nuevo) ← React no se entera // ✅ BIEN: setEstudiantes([...estudiantes, nuevo]) ← React redibuja

🔄 useEffect — «Cuando pase X, haz Y»

Imagínalo así:

useEffect es como poner un aviso en la puerta: «cuando abras esta página, ve a buscar los datos al servidor». El arreglo [] del final significa «hazlo solo una vez, al cargar». Si pones algo dentro del arreglo (ej: [id]), se ejecuta cada vez que ese valor cambia.

useEffect — patrones con peticiones HTTP // ════ PATRÓN 1: Cargar datos al montar el componente ════ useEffect(() => { load(); // ← llama a nuestra función async }, []); // ← [] = solo al abrir la página (una vez) async function load() { setLoading(true); // 🔄 Mostrar spinner setError(null); // 🧹 Limpiar errores anteriores try { const data = await estudiantesService.findAll(); setEstudiantes(data); // ✅ Guardar datos → React redibuja } catch { setError('No se pudieron cargar los estudiantes'); } finally { setLoading(false); // 🏁 Siempre ocultar spinner al terminar } } // ════ PATRÓN 2: Reaccionar cuando cambia el ID ════ useEffect(() => { if (selectedId) estudiantesService.findOne(selectedId).then(setDetail); }, [selectedId]); // ← se ejecuta cada vez que selectedId cambie // ════ PATRÓN 3: Limpiar al desmontar (evitar memory leaks) ════ useEffect(() => { const controller = new AbortController(); fetch(url, { signal: controller.signal }); return () => controller.abort(); // ← cancela si el usuario navega }, [url]);

🗺️ El ciclo completo: abrir página → ver datos

El return de un componente según el estado return ( <div> {/* 1️⃣ Mostrar spinner mientras carga */} {loading && ( <div className="flex justify-center p-8"> <div className="animate-spin h-8 w-8 border-4 border-blue-500 rounded-full"/> </div> )} {/* 2️⃣ Mostrar error si lo hay */} {error && ( <div className="bg-red-100 border border-red-400 text-red-700 p-4 rounded"> ❌ {error} </div> )} {/* 3️⃣ Mostrar datos si llegaron */} {!loading && !error && estudiantes.length === 0 && ( <p>No hay estudiantes registrados aún.</p> )} {!loading && estudiantes.map(est => ( <div key={est.id}>{est.nombres} {est.apellidos}</div> ))} </div> );

🎯 El portero del backend

El Controller en NestJS es como el portero de un edificio. Tiene una lista de quién puede entrar: @Get(), @Post(), etc. Cuando alguien llama (petición HTTP), el portero la recibe y la pasa adentro al Service. ¡Nunca sale de su puesto!

backend/src/modules/estudiantes/controller/estudiantes.controller.ts @Controller('estudiantes') // 🏠 Mi dirección es /api/v1/estudiantes export class EstudiantesController { // NestJS me da el Service automáticamente (magia 🪄) constructor(private readonly svc: EstudiantesService) {} @Get() // 📥 GET /estudiantes → dame TODOS findAll() { return this.svc.findAll(); } @Get(':id') // 📥 GET /estudiantes/5 → dame el #5 findOne(@Param('id', ParseIntPipe) id: number) { return this.svc.findOne(id); } @Post() // 📤 POST /estudiantes → crea uno nuevo create(@Body() dto: CreateEstudianteDto) { return this.svc.create(dto); } @Get(':id/historial') // 📊 GET /estudiantes/1/historial → historial académico historial(@Param('id', ParseIntPipe) id: number) { return this.svc.historial(id); } }

📦 Los «moldes» de los datos

En el backend hay dos tipos de clases que describen la forma de los datos. Son como fichas técnicas: una describe cómo luce un objeto en la base de datos (Entity) y otra describe qué datos debe traer el cliente al crear o actualizar algo (DTO). Son distintas a propósito.

📦 Entity — el «carné» del objeto

La Entity es la clase TypeScript que representa exactamente cómo está el dato guardado en la base de datos. Tiene todos los campos, incluidos los que genera la BD automáticamente (id, createdAt, updatedAt). Es solo una descripción — no tiene decoradores de validación.

estudiante.entity.ts export class EstudianteEntity { // ← generado por la BD id: number; nombres: string; apellidos: string; codigoEstudiantil: string; documentoIdentidad: string; correoInstitucional: string; fechaNacimiento: Date; programaAcademicoId: number; // ← gestionados por Prisma createdAt: Date; updatedAt: Date; }
📝 DTO — el «formulario» de entrada

El DTO (Data Transfer Object) describe solo los campos que el cliente debe enviar. No tiene id ni createdAt porque eso lo pone el servidor. Cada campo lleva decoradores de validación (@IsString, @IsEmail…) que el ValidationPipe usa para revisar la petición.

create-estudiante.dto.ts export class CreateEstudianteDto { @IsString() nombres: string; @IsString() apellidos: string; @IsString() codigoEstudiantil: string; @IsEmail() correoInstitucional: string; @IsDateString() fechaNacimiento: string; @IsInt() programaAcademicoId: number; // ← sin id, createdAt, updatedAt }

🔄 ¿Cómo fluyen Entity y DTO?

El DTO entra por el Controller (validado por el ValidationPipe), el Service lo procesa y el Repository lo usa para crear el registro. La base de datos devuelve el objeto completo, que Prisma mapea a un objeto que coincide con la Entity. Ese es el dato que viaja de vuelta al frontend.

🖼️ La analogía del pedido de pizza

📝 DTO
Lo que escribes en la comanda: «pizza mediana, queso extra»
→
👨‍🍳 Service / Repo
El chef la prepara y la registra en el sistema
→
🧾 Entity
El ticket completo: número de orden, hora, ingredientes, precio

¿Por qué no usar la misma clase para todo?

Si usaras la Entity como DTO, el cliente podría enviarte id: 99 o createdAt: "1900-01-01" y sobreescribir datos de la base de datos. Con el DTO controlamos exactamente qué puede entrar. ¡Es una capa de seguridad!

🧠 El cerebro pensante

El Service es el más inteligente de los 3. Conoce las reglas: "no puede haber dos estudiantes con el mismo código", "no puedes matricularte en algo que no existe". Cuando algo está mal lanza una excepción: es como levantar la mano para decir "¡espera, algo está mal aquí!"

backend/src/modules/estudiantes/service/estudiantes.service.ts @Injectable() export class EstudiantesService { constructor(private readonly repo: EstudiantesRepository) {} // ✅ findAll: simplemente pedir al repo la lista findAll() { return this.repo.findAll(); } // ✅ findOne: verificar que exista async findOne(id: number) { const est = await this.repo.findOne(id); if (!est) // 🚨 Si no existe → error 404 Not Found throw new NotFoundException( `Estudiante #${id} no encontrado` ); return est; } // ✅ create: intentar crear, atrapar duplicados async create(dto: CreateEstudianteDto) { try { return await this.repo.create(dto); } catch (e) { if (e.code === 'P2002') // 🚨 Código UNIQUE de Prisma → error 409 Conflict throw new ConflictException('Ya existe ese estudiante'); throw e; } } }

💾 El que habla con la base de datos

El Repository es el único que sabe cómo hablar con PostgreSQL. Usa Prisma, que es como un traductor: convierte código TypeScript bonito en SQL aburrido. prisma.estudiante.findMany() se convierte en SELECT * FROM estudiantes. ¡El Service no sabe SQL ni necesita saberlo!

backend/src/modules/estudiantes/repository/estudiantes.repository.ts @Injectable() export class EstudiantesRepository { constructor(private readonly prisma: PrismaService) {} // → SELECT * FROM estudiantes ORDER BY id ASC findAll() { return this.prisma.estudiante.findMany({ include: { programaAcademico: true }, // LEFT JOIN orderBy: { id: 'asc' }, }); } // → SELECT * FROM estudiantes WHERE id = $1 findOne(id: number) { return this.prisma.estudiante.findUnique({ where: { id }, include: { programaAcademico: true }, }); } // → INSERT INTO estudiantes (...) VALUES (...) create(dto: CreateEstudianteDto) { return this.prisma.estudiante.create({ data: { ...dto, fechaNacimiento: new Date(dto.fechaNacimiento), }, include: { programaAcademico: true }, }); } // → DELETE FROM estudiantes WHERE id = $1 remove(id: number) { return this.prisma.estudiante.delete({ where: { id } }); } }

¿Qué es include?

En SQL se llama JOIN: unir dos tablas. include: { programaAcademico: true } le dice a Prisma: "además del estudiante, tráeme también los datos del programa al que pertenece". Así en la respuesta viene todo junto, sin hacer dos consultas.

❌ ¿Qué pasa cuando algo sale mal?

Los errores son normales. La diferencia entre un buen sistema y uno malo es cómo maneja los errores. Nuestro sistema tiene un "guardabosques" para cada tipo de problema. 🌲

🟡 Error 400 — "Mandaste datos incorrectos"
❌ Lo que pasa

El frontend envía un formulario con el email con formato incorrecto o falta un campo obligatorio.

POST /api/v1/estudiantes { "nombres": "Juan", "correoInstitucional": "esto-no-es-email" // ← ❌ falta @ }
✅ La respuesta del backend

El ValidationPipe detecta el error ANTES de llegar al Controller y responde automáticamente:

{ "statusCode": 400, "message": [ "correoInstitucional must be an email" ], "error": "Bad Request" }
🔴 Error 404 — "No existe lo que buscas"
❌ Lo que pasa

El frontend pide el estudiante con ID 999 que no existe en la base de datos.

GET /api/v1/estudiantes/999
✅ El Service lanza la excepción

El Service encuentra null en el Repository y lanza NotFoundException. El HttpExceptionFilter la formatea:

{ "statusCode": 404, "message": "Estudiante #999 no encontrado", "error": "Not Found" }
🔴 Error 409 — "Ya existe uno igual"
❌ Lo que pasa

Intentas crear un estudiante con un código que ya existe (restricción UNIQUE en PostgreSQL).

POST /api/v1/estudiantes { "codigoEstudiantil": "EST-2026-001" // ← Ya existe }
✅ Prisma P2002 → ConflictException

Prisma devuelve error código P2002. El Service lo atrapa y lanza ConflictException:

{ "statusCode": 409, "message": "Ya existe ese estudiante", "error": "Conflict" }

🛡️ Los dos guardianes del error

ResponseInterceptor: envuelve TODAS las respuestas exitosas en { statusCode, message, data }.
HttpExceptionFilter: atrapa TODOS los errores y los convierte en JSON legible. Sin él, el error sería un HTML gigante e incomprensible.
